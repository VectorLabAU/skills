# UI, UX, Microcopy & Taste Skills System — Architecture, File Structure & Generation Specification

This specification defines a modular system of UI/UX, microcopy, and visual taste skills modeled after the architecture of Matt Pocock's skills. It is engineered specifically for AI Coding Agents (Cursor, Windsurf, Claude Code, GitHub Copilot) to deterministically generate, critique, and refine low-friction, high-taste user interfaces across any product domain or frontend stack.

---

## 1. System Tenets

### Deterministic Agent Guidance

Skills provide binary, testable constraints rather than vague design generalities. Agents are given explicit rules on layout mechanics, validation lifecycles, and copy conventions.

### Friction is the Enemy

Every input, click, transition, modal, and delay must justify its existence. Non-destructive operations execute with smart defaults and instant feedback; complex actions are decoupled into measured stages.

### Taste is Geometric & Typographic Discipline

Taste is not decorative flair; it is strict baseline grids, optical alignment, deliberate restraint in color distribution, depth layering, and rhythmic whitespace.

### Copy as Interaction Mechanics

Microcopy is an active interface component. It directs action with verb-first syntax, eliminates blame during failure, and removes cognitive overhead.

### Code & Framework Agnostic

Guidance relies on CSS primitives, DOM state machines, web standards, and visual geometry, allowing it to apply universally across React, Vue, Svelte, Angular, native web components, or mobile platforms.

## 3. Skill File Anatomy & Frontmatter Standard

Every `SKILL.md` must follow this exact machine-readable schema:

```yaml
---
name: [kebab-case-slug]
title: [Clear Descriptive Title]
category: [visual-taste | interaction-friction | microcopy-voice | state-feedback | setup]
severity: [hard-rule | heuristic | polish]
triggers:
  - "[Contextual scenario, e.g., 'Writing form inputs or modals']"
  - "[Keywords / File patterns]"
references:
  - "reference/[relative-file-name].md"
---
```

**Agent Skills requirement:** In addition to the fields above, every skill consumed by Agent Skills / skills.sh must include a `description` field. The description must state **WHAT** the skill does and **WHEN** an agent should use it (third person, under 1024 characters, with trigger phrases).

Example:

```yaml
---
name: form-mechanics-and-validation
description: "Blur-first validation, clickable submit, and fewer fields. Use when building forms, inputs, wizards, or fixing validation UX."
title: Form Mechanics and Validation
category: interaction-friction
severity: hard-rule
---
```

### Body Structure

Each skill body follows this shape:

#### Intent

A concise statement of the ergonomic, cognitive, or aesthetic goal.

#### Hard Rules (Non-Negotiable)

Binary, testable requirements that AI agents and linters must verify without ambiguity.

#### Design Heuristics & Taste Principles

Guidance on proportions, optical weight, spacing, and micro-behavior.

#### Concrete Scenarios (Before vs. After)

##### ❌ Anti-Pattern (High Friction / Bad Taste)

Exact representation of the common failure mode with explanation.

##### ✅ Best Practice (Low Friction / High Taste)

Exact layout/interaction model that satisfies all rules.

#### Framework-Agnostic Implementation Blueprint

Pseudocode, state-machine transitions, or CSS layout strategies (zero third-party library dependencies).

#### Agent Checklist

Step-by-step verification checklist for an AI agent completing a task in this domain.

## 4. Detailed Specification of Core Skills

### 4.0 Setup & Configuration Skill

**Path:** `setup-ui-ux-skills/SKILL.md`

**Purpose:** Interactive agent interview modeled after Matt Pocock's setup skill. When run, the agent questions the user across four fundamental vectors and writes a concrete `.ux-profile.md` at the project root.

**Vectors configured:**

- **Reference Standard:** Linear / Stripe / Raycast / Things 3 / Apple macOS / Custom
- **Anti-Aesthetic Banned List:** Gratuitous glassmorphism, floating pill badges, arbitrary gradients, neon glowing borders, cartoon empty-state illustrations, nested scrollbars
- **Accessibility Target:** Strict WCAG 2.1 AAA (highest contrast/sizing priority) vs. WCAG 2.1 AA (balanced with subtle visual restraint)
- **Brand Tone:** Cold Utilitarian (Linear/Stripe) vs. Warm Humancentric (Notion/Slack) vs. Direct Opinionated (Basecamp)

**Output:** Generates and commits `.ux-profile.md`, which all other skills ingest as dynamic context.

---

### 4.1 Visual Taste & Layout

#### 1. layout-geometry-and-grids

**Hard Rules:**

- Standardize on an 8pt spatial grid for major components, 4pt for micro-spacings (padding, icons)
- Maximum body line length constrained to 65–75 characters (`ch` units)
- Elements sharing visual hierarchy must maintain uniform optical baselines
- Icon-to-text alignments must align to the font's cap-height, not the total bounding box

**Companion Reference:** `reference/optical-offsets.md` (exact mathematical vertical shifts for SVGs and labels)

#### 2. typography-and-hierarchy

**Hard Rules:**

- Maximum 3 font weights across the entire application (e.g., 400 Regular, 500 Medium, 600 Semi-bold). Never use >700
- Scale step constraint: Body text = 1rem (16px base); secondary text = 0.875rem (14px); minimal legal/meta = 0.75rem (12px). No text below 12px anywhere
- Line-height must decrease as font-size increases: Display/Headings at 1.1–1.25, Body text at 1.5–1.6

**Companion Reference:** `reference/scale-math.md` (type scales: Major Second vs. Minor Third)

#### 3. restrained-color-and-depth

**Hard Rules:**

- Surface color distribution strictly adheres to 60-30-10: 60% dominant canvas/background, 30% structural surface (cards, sidebars), 10% purposeful accent (interactive elements)
- Elevation must be achieved via border contrast first (1px subtle boundary), supplemented by soft, diffused shadows with low alpha (<0.08 in light mode, subtle edge lighting in dark mode). Never use hard drop-shadows

**Companion Reference:** `reference/elevation-tokens.md` (surface hierarchy table from canvas level 0 to overlay level 3)

#### 4. anti-ai-slop

**Hard Rules — explicit ban on:**

- Multi-color radial rainbow gradients on standard CTA buttons
- Glassmorphic blur (`backdrop-filter`) without high-contrast boundary containment
- Generic cartoon vector illustrations depicting people waving or high-fiving in empty states
- Icon bloat: No icons inside inputs unless functional (e.g., search magnifier or clear button)
- Unnecessary pill-shaped containers around standard text metadata

**Companion Reference:** `reference/slop-checklist.md` (visual identification matrix for generic SaaS clutter)

---

### 4.2 Interaction & Low-Friction

#### 5. surface-routing-and-dialogs

**Hard Rules (Direct User Constraints):**

- Estimated task completion **< 10 seconds:** Use a Slide-over (drawer) or non-modal popover. Do not navigate away from context
- Estimated task completion **≥ 10 seconds** or multi-step: Require a dedicated sub-page or URL route. Stacking modals is strictly prohibited
- Single field edits: Require in-place inline expansion with 0 layout shift (reserve sizing or use absolute overlay positioning)
- **Destructive Operations (All):** Strictly require a dedicated confirmation dialog
  - Must state the exact entity being destroyed (e.g., "Delete workspace 'Analytics'?" not "Are you sure?")
  - Action button must explicitly name the destructive verb (e.g., "Delete Workspace", colored in destructive red/crimson)
  - Cancel button must be default keyboard focus (Escape dismisses)

**Companion Reference:** `reference/destructive-actions.md` (spec for confirmation modal layouts and focus trapping)

#### 6. form-mechanics-and-validation

Built from framework-agnostic industry best practices.

**Hard Rules:**

**Validation Lifecycle:**

- Never mark an input invalid while the user is actively typing in a pristine field
- Trigger error validation on initial blur event
- Once marked invalid, clear the error state immediately on focus or on the first corrective keystroke (reward early, punish late)

**Field Discipline:**

- Eliminate redundant fields: Infer city/state from postal code; use single "Full Name" field over First/Last unless legally separated
- Disabled buttons are prohibited for submit actions: Keep the button clickable and show inline validation alerts on click if fields are incomplete, rather than trapping the user with a silent dead button

**Companion Reference:** `reference/form-best-practices.md` (keyboard submit, auto-complete attributes, input masking)

#### 7. keyboard-and-focus-parity

**Hard Rules:**

- Every interactive element accessible via mouse must be operable via keyboard (Tab, Shift+Tab, Enter, Space)
- Native focus rings must never be set to `outline: none` without an immediate, high-contrast custom replacement (`box-shadow` or `outline-offset: 2px`)
- Modals and slide-overs must trap keyboard focus internally and restore focus to the triggering element upon closure

**Companion Reference:** `reference/keybinding-matrix.md` (universal command bar shortcuts, grid table navigation)

#### 8. smart-defaults-and-inference

**Hard Rules:**

- Never present a blank dropdown where an intelligent default can be inferred from user timezone, locale, or previous selection
- Form drafts must automatically persist to local memory so accidental navigation or tab closure results in 0 data loss

**Companion Reference:** `reference/state-persistence.md` (draft auto-save heuristics and cache invalidation)

---

### 4.3 Microcopy & Voice

#### 9. verb-first-actions

**Hard Rules:**

- Every CTA, button, and action link must begin with a strong, unambiguous imperative verb (e.g., "Export CSV", "Create Project", "Connect Repository")
- Ban ambiguous labels: "OK", "Submit", "Proceed", "Continue" (unless part of a multi-step sequential wizard)
- Title capitalization or sentence capitalization must be uniform throughout the system (default: Sentence case for UI copy and buttons, e.g., "Save changes")

**Companion Reference:** `reference/verb-dictionary.md` (permitted verb pairings and action-object syntax)

#### 10. blameless-system-recovery

**Hard Rules:**

- Microcopy must never blame the user (e.g., ban "You entered an invalid email", use "Enter an email address like name@domain.com")
- Errors must answer three things in <2 sentences:
  1. What happened (plain human terms, zero raw HTTP or database codes)
  2. Why it matters (impact on their data)
  3. What immediate step recovers the state (e.g., "Check your internet connection and retry")
- Technical errors must provide a one-click "Copy error details" utility for support instead of dumping stack traces into the UI

**Companion Reference:** `reference/error-taxonomy.md` (toast vs inline vs full-page error copy templates)

#### 11. label-and-placeholder-discipline

**Hard Rules:**

- Placeholders must NEVER substitute for input labels. Placeholders disappear on input and destroy accessibility and cognitive reference
- Placeholders may only contain formatting examples or syntax hints (e.g., `acme-corp` or `MM/YY`)
- Every form input must possess an associated, visible label

**Companion Reference:** `reference/placeholder-rules.md` (accessible label bindings and helper text placements)

---

### 4.4 State Transitions & Feedback

#### 12. latency-masking-and-loaders

**Hard Rules:**

- Duration **< 100ms:** Execute immediately without showing any loader or spinner (showing a loader under 100ms causes visual flickering)
- Duration **between 100ms and 1000ms:** Use an inline spinner or status indicator localized to the triggering button
- Duration **> 1000ms** for full-page or content blocks: Render a structural skeleton screen matching the geometric layout of the incoming content. Never use a giant full-page centered spinner

**Companion Reference:** `reference/timing-benchmarks.md` (perceptual latency thresholds and skeleton shimmer rhythm)

#### 13. empty-states-and-activation

**Hard Rules:**

Zero states must never present dead ends. Every empty state must contain:

- A clear header stating what belongs here
- A one-sentence explanation of the value of populating this view
- A primary CTA button triggering the creation or import flow immediately

Filtered search empty states ("No results found") must include a one-click action to "Clear all filters".

**Companion Reference:** `reference/activation-patterns.md` (initial onboarding empty states vs. zero-search result patterns)

## 5. Setup Skill Interview Protocol

Below is the concrete design for the interactive setup skill file, showing how an AI Coding Agent runs the onboarding interview to configure the workspace:

```yaml
---
name: setup-ui-ux-skills
title: UI/UX & Taste System Setup Wizard
category: setup
severity: hard-rule
triggers:
  - "When the user initializes the skills library"
  - "When setting up UI/UX standards for a new project"
  - "Run setup-ui-ux-skills"
references:
  - "reference/taste-archetypes.md"
  - "reference/anti-patterns.md"
---
```

### Intent

Conduct an interactive interview to initialize `.ux-profile.md` at the project root. This profile defines the aesthetic baseline, accessibility targets, forbidden design patterns, and voice tone used by all downstream skills.

### Interview Protocol (Agent Prompt Rules)

The agent must present the following 4 questions one at a time or in a concise structured prompt, awaiting user input:

#### 1. Aesthetic Reference Standard

- [1] Linear (Monochrome, high density, sharp 1px borders, technical speed)
- [2] Stripe (Refined typography, balanced depth, elegant data tables, high clarity)
- [3] Apple Native (Generous spacing, unified radii, fluid transitions, neutral palettes)
- [4] Raycast (Keyboard-first, ultra-compact, high contrast, pure utility)
- [5] Custom (User provides custom reference URLs or principles)

#### 2. Visual Anti-Aesthetic (Things to aggressively ban)

Provide a recommended list of bans (AI slop, gratuitous glassmorphism, floating pastel pill tags, cartoon illustrations, rainbow CTA gradients).

Prompt: "Confirm this ban list or add/remove specific patterns."

#### 3. Accessibility Target

- [A] Strict WCAG 2.1 AAA: Contrast > 7:1 for normal text, larger minimum touch targets (48×48px), prominent focus outlines
- [B] WCAG 2.1 AA (Balanced Taste): Contrast > 4.5:1 for normal text, 3:1 for large text/borders, refined focus rings (44×44px targets)

#### 4. Brand Tone & Microcopy Voice

- [1] Utilitarian & Minimal (Cold, precise, invisible. e.g., Linear, Stripe)
- [2] Warm & Humancentric (Clear, empathetic, supportive. e.g., Notion, Slack)
- [3] Opinionated & Direct (Punchy, editorial, concise. e.g., Basecamp)

### Output Artifact

Upon completion, the agent MUST write `.ux-profile.md` to the root directory with the chosen settings and display a confirmation message summarizing the active configuration.

## 6. Execution Rules for AI Coding Agents

When any coding agent operates within a project utilizing this skills library:

### Read `.ux-profile.md` First

Before modifying or creating any component, CSS rule, or microcopy, read `.ux-profile.md` to ground tone, contrast, and visual references.

### Consult Associated Skills

When generating forms, read `form-mechanics-and-validation`; when creating overlays or navigation, read `surface-routing-and-dialogs`. Match the domain skill to the task at hand.

### Run the Pre-Flight Taste Audit

Before shipping UI changes, verify:

- Does this introduce any item on the banned anti-aesthetic list?
- Is there any modal where an inline edit or slide-over was mandated (<10s rule)?
- Are destructive actions equipped with clear, explicit confirmation modals?
- Is all copy verb-first and free of user blame?
- Does all validation fire on blur and clear immediately on focus/edit?
